# docs/math — worked mathematical derivations

The [`journey_of_a_model/`](../../journey_of_a_model/) journal explains
*what* each component does and *why*, with one worked numeric example per
formula. This folder is the companion that goes the other direction:
**one component at a time, every operation derived from first principles
and then executed by hand**, with a single concrete set of tensors carried
from the first line to the last so you can watch each array change shape
and value at every step.

Each entry here mirrors a journal entry number (`004-attention-gqa.md`
here ↔ `journey_of_a_model/004-attention-gqa.md`) and is meant to be read
*after* the journal entry, when you want the full ledger rather than the
summary.

## Conventions

- **No fabricated numbers.** Every intermediate value printed in a
  derivation is reproduced by a runnable script in this folder that pins
  the same weights into the *real* `qwenmoe/` module and asserts the
  hand-computed result. If a script isn't named in the doc, the numbers
  aren't trustworthy yet.
- **Nothing is defined with an undefined term.** Same bar as the journal
  (see [its README](../../journey_of_a_model/README.md)).
- **Exact vs. empirical is always marked.** A step that is provable
  algebra says so; a constant that is an empirical choice (a paper's
  slope schedule, a base frequency) says that instead.
- **Citations are found, not guessed** — every paper link was confirmed
  by search.

## Which example does each doc use?

**The docs do not share one example.** Each doc follows rule 1 below
("one running example, carried end to end") *within itself*; across docs,
the examples come in a few families. The project grew over many
iterations (GQA → MoE → full model → training → modernization →
scaling), and each component needed a different smallest example to
exercise its own behaviours (e.g. 005 needs an expert that gets zero
tokens; 022 needs `head_dim = 4` so the RMS is a real average; 007 needs
no model at all). So there are deliberate **cuts** between families, and
**threads** within them. Always check the family before comparing numbers
across docs.

**The cuts to be aware of:**

- **004 (attention) and 005 (MoE) are not the attention and MoE that doc
  006 runs.** 006 treats both as black boxes and uses its own, different
  tensors (identity-style attention weights; `d=4`, `N=2`, `k=1` MoE).
  Their derivations hold for any weights, but you cannot take 004's output
  and feed it into 005's input — the widths (`d=4` vs `d=2`) don't even
  match.
- **006's attention and MoE steps are checked against the real modules by
  the verify script, not re-derived by hand.** The by-hand derivations of
  those operations live in 004 and 005, on their own tensors. The bridge
  script [`verify_bridge_004_005_into_006.py`](verify_bridge_004_005_into_006.py)
  closes this gap numerically: it runs 004's attention steps and 005's MoE
  steps on the exact tensors 006's model feeds each block and re-assembles
  006's whole forward pass from them (agreement about $10^{-7}$). The
  *arithmetic* is therefore verified on 006's tensors; the digit-by-digit
  *walkthrough* still lives on 004/005's examples.
- **There is no math doc for 003 (RMSNorm and positional encoding).** The
  RMSNorm arithmetic appears inside 006 (Steps 4, 7, 16) and 022; RoPE
  appears as a step inside 004 and 016.
- **Journal entries 042 and 043 have no math doc, deliberately.** 042 (CUDA device plumbing, the async-timer fix) and
  043 (host-device sync counting, 362 → 20 per step) are engineering and measurement, not derivation: there is no
  formula to solve by hand, and the counts are runtime observations on specific hardware. 039–041 are covered by
  [039](039-bpe-incremental-counts-and-streaming.md) (which also covers 040) and
  [041](041-step-offset-sampler-and-long-run-arithmetic.md); 044–045 by [044](044-mfu-and-the-roofline.md).
  The 006 model is still the intended spine for anything that needs a *toy* model; 044 deliberately uses the real
  `SCALE_300M` preset because its subject is a measured run.

**How to add a new doc consistently:** if it needs a model, reuse family D
(006's model and weights) and say so in its Part 1, as 010/011/018/024/038
do. If it extends attention or MoE, reuse family A or C unchanged, as
021/025/027/031 do. Only define a new example when none of these can
exercise the component, and then state which family it breaks from and why.

## Prompt to generate a new entry

Paste this into a fresh session, filling in the two blanks. It reproduces
the process that produced `004-attention-gqa.md`.

> Write a `docs/math/<NN>-<slug>.md` — a complete, first-principles,
> **solved-by-hand** derivation of **<COMPONENT>** (implemented in
> `<path/to/module.py>`), as a companion to the journal entry
> `journey_of_a_model/<NN>-<slug>.md`. Requirements:
>
> 1. **One running example, carried end to end.** Pick the smallest tensor
>    shapes and simplest fixed weights that still exercise every behaviour
>    of the component (e.g. for GQA, `n_kv_heads < n_heads`). Write out
>    every input tensor and weight matrix explicitly at the top. Never
>    switch examples partway.
> 2. **Follow the real code path, line by line.** Walk the actual module
>    (the `forward_with_trace` / explicit path if one exists), citing
>    `file.py:line`. Don't skip a single operation — a reshape, a
>    transpose, a broadcast all get their own step.
> 3. **For every operation: first derive, then compute.** Explain *why* the
>    operation has the form it does (derive any formula in full, not just
>    the result), then do the arithmetic **digit by digit** — matrix
>    multiplies entry by entry, softmax with real exponentials, etc.
> 4. **Trace the tensor.** After each step state the shape before → after
>    and show which numbers moved where. Keep a running "shape ledger".
> 5. **Define every term at first use** (vector, dot product, variance,
>    …). Never define one unexplained term with another. Assume no
>    linear-algebra background.
> 6. **Mark exact vs. empirical.** Provable algebra says so; an
>    empirically-chosen constant (a base frequency, a slope schedule) says
>    that instead.
> 7. **No fabricated numbers.** Write `docs/math/verify_<NN>_<slug>.py`
>    that pins the same weights into the *real* `qwenmoe/` module, runs it,
>    prints every intermediate, and `assert`s the hand-computed
>    end-to-end result (and any key property). Run it; quote its real
>    output in the doc. If a fused/optimised path exists, show the two
>    agree and report the measured max difference.
> 8. **Citations found, not guessed.** Web-search every paper link and
>    confirm it before citing. Reuse the journal entry's existing links
>    where they overlap.
> 9. **Diagrams:** at least one Mermaid diagram of the data flow.
> 10. Close with a cost/why-built-this-way section using the example's own
>     numbers, a "Questions that might come to mind" section, a symbol
>     table, and the citation list.
> 11. Add the entry to the table in `docs/math/README.md` and a one-line
>     pointer blockquote near the top of the journal entry.
> 12. Add the doc's row to `DOCS` (and any new boxes/edges to `NODES`/`EDGES`) in
>     `docs/math/build_architecture_footer.py`, then run it to generate the
>     doc's closing architecture diagram.
