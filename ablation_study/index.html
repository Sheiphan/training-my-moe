What each architectural choice actually costs

Every row on this page is a real training run. Each one changes exactly one thing, trains on the identical fixed token slice for the identical step budget, and reports what that single change did to validation loss, throughput and expert routing. Every number is read from a real train.jsonl written by Trainer.fit — none of it is illustrative.

A different experiment from the one above

This tier is not comparable with the single-axis study: it uses a different base config (BASELINE, d_model 256 × 6 layers, not the tiny SMOKE_TEST), a different token slice and budget, and — crucially — it changes several axes at once, because the question here is not "what does one knob do" but "what should the recommended configuration be after the modernization spec". It also trains every variant over two seeds, so a difference can be checked against seed noise instead of eyeballed.

Routing load per expert

Real dispatched-token counts per layer at the final logged step. FINEGRAINED has 32 narrow experts where the others have 8 wide ones, so its bars are both more numerous and individually smaller — the dashed line is each model's own even share.

How evenly is that load spread?

One dot per layer. Coefficient of variation = std(load) / mean(load): zero means every expert received an identical share, larger means the router is playing favourites.
